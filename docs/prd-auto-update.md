# PRD — 自动更新（Auto Update）

> 独立需求文档。总纲见 [`prd.md`](prd.md)（本文件由其中 FR-10 引入）。
> 技术实现见 [`tdd-auto-update.md`](tdd-auto-update.md)。

## 1. 背景

O Muse 以「curl 一键安装 + gh-pages 托管」的公测方式分发（见
[`tech-release-without-developer-id.md`](tech-release-without-developer-id.md)）。
这种分发没有 App Store 的自动更新，也没有 Sparkle 之类的成熟框架集成。

结果是：用户装完就停在那个版本。发新版后，除非用户碰巧看到 Release 页，
否则不会升级——**修好的 bug 到不了用户手上**，公测反馈循环断掉。

而我们的安装方式本身已具备自动更新的全部前提：

- 版本号有单一来源（`tauri.conf.json`）
- 产物有 SHA256 校验
- gh-pages 上有稳定的 `releases/latest/` 入口
- 应用是自包含的 `.app`（替换即可，无需迁移用户数据）

因此自动更新是**低成本、高收益**的能力。

## 2. 目标与非目标

### 目标

1. 应用能**自动感知**有新版本，无需用户主动检查。
2. 有新版本时**明确告知**用户：版本号、更新内容要点、体积。
3. 用户点一下即可**自动完成**下载、校验、替换、重启。
4. 全程**不打断**用户工作：下载不阻塞界面，用户可推迟。
5. 更新包**必须验签**，防止中间人替换。

### 非目标

- 不做增量/差量更新（`.app` 全量替换即可，公测期体积可接受）。
- 不做灰度发布、A/B 渠道、强制升级。
- 不做回滚到旧版本（用户可重新运行安装命令装指定版本）。
- 不支持 Windows/Linux（当前仅 macOS）。

## 3. 用户故事

| # | 场景 | 期望 |
|---|---|---|
| U1 | 我打开应用，后台已发现新版本 | 顶部出现一条**不刺眼**的提示条：「有新版本 0.2.0 可用」 |
| U2 | 我想知道这版改了什么 | 点提示条展开，看到版本号、要点、下载体积 |
| U3 | 我正在编曲，不想现在更新 | 点「稍后」，提示条收起；本次会话不再打扰 |
| U4 | 我现在就更新 | 点「更新」→ 看到下载进度 → 完成后自动重启，直接是新版本 |
| U5 | 我网络不好，下载中断 | 明确报错并保留重试入口，不留下半成品 |
| U6 | 我关心安全 | 更新包经**签名校验**；校验失败则拒绝安装并明示原因 |
| U7 | 我不想被自动检查打扰 | 设置页可关闭「自动检查更新」，但保留手动「检查更新」 |
| U8 | 我离线 | 静默失败，不弹错误、不打扰；恢复网络后下次自动再试 |

## 4. 功能需求

### FR-U1 自动检查

- 应用启动后**延迟数秒**再检查（避免与启动争抢资源）。
- 之后**周期性**检查（默认每 6 小时）。
- 检查为**静默**：无更新、离线、请求失败都**不打扰用户**。
- 检查频率与开关可在设置页调整/关闭。

### FR-U2 更新提示

- 检测到新版本时，在主界面**顶部**显示提示条（非模态、不阻塞）。
- 提示条至少包含：当前版本 → 新版本号。
- 可展开查看：**更新要点**（Release notes）、下载体积。
- 提供两个动作：「稍后」与「更新」。
- 「稍后」后**本次会话不再提示**（下次启动可再提示）。

### FR-U3 下载与安装

- 点击「更新」后显示**下载进度**（百分比 + 已下载/总量）。
- 下载完成后显示「安装并重启」或直接自动重启（用户可在设置中选择）。
- 安装过程**必须**先验签，验签失败 → 中止并提示「更新包校验失败，已取消安装」。
- 安装期间不允许重复触发；失败后保留重试入口。
- 更新后**用户数据保留**（license、偏好、插件缓存、分轨运行时都在
  `~/Library/Application Support/work.xsin.omuse/`，不在 `.app` 内）。

### FR-U4 重启

- 安装完成后自动重启到新版本。
- 重启是**用户可见且已同意**的（不静默杀进程）；若用户有未完成的分轨任务，
  需提示「分轨任务将中断」。

### FR-U5 设置与手动检查

设置页提供：

| 项 | 说明 |
|---|---|
| 当前版本 | 只读展示 |
| 自动检查更新 | 开关，默认开 |
| 检查更新 | 手动触发，立即反馈结果（已是最新 / 有新版本 / 检查失败原因） |
| 更新通道 | 只读展示当前更新源地址（可审计） |

### FR-U6 静默失败的边界

以下情况**不弹错误**，只记录：网络不可达、DNS 失败、超时、服务端 5xx。
以下情况**必须提示**：验签失败、磁盘空间不足、替换失败。

## 5. 非功能需求

- **安全**：更新包必须通过**独立于 Apple 证书的签名校验**（Tauri updater 密钥对）。
  私钥只存在于 CI Secrets，**绝不进入仓库或客户端**。
- **可用性**：检查更新不得阻塞界面；下载在后台进行，界面保持可用。
- **可审计**：设置页展示更新源 URL；用户可自行核对。
- **低打扰**：单次会话最多提示一次；「稍后」即生效。
- **磁盘**：安装前检查可用空间（更新包 + 解压后 ≈ 2× 应用体积）。

## 6. 验收标准

1. 旧版本启动后能自动发现新版本并显示提示条。
2. 点「更新」能完成下载（有进度）→ 验签 → 替换 → 自动重启，重启后版本号为新版。
3. 篡改更新包后点击更新，**必须拒绝安装**并提示校验失败。
4. 断网时检查更新**不产生任何可见错误**，界面正常。
5. 「稍后」后本次会话不再提示。
6. 关闭自动检查后不再自动请求；手动检查仍可用。
7. 更新后 license、设置、插件缓存、分轨运行时均保留。
8. 磁盘不足时给出明确提示且不破坏现有安装。

## 7. 成功度量

- 新版发布后 7 天内，活跃用户升级比例。
- 自动检查失败率（应为极低；失败即不打扰，但需可观测）。
- 更新失败率与失败原因分布（验签/磁盘/网络）。

## 8. 风险与缓解

| 风险 | 缓解 |
|---|---|
| 更新把应用换坏，用户无法启动 | 更新包经签名校验；替换前备份旧 `.app`，失败则回滚 |
| 用户正在分轨时被重启打断 | 重启前检测进行中的任务并明确提示 |
| 私钥泄漏导致可被投毒 | 私钥仅存 CI Secrets；轮换密钥需发一次公告让用户手动重装 |
| 频繁提示打扰用户 | 单会话一次 + 「稍后」+ 可关闭自动检查 |
| 更新源不可用 | 静默失败，不影响应用正常使用 |
